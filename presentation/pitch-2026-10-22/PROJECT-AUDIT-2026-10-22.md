## Найденные проблемы и запросы владельцу backend/cloud

### 1. Облачный сценарий защиты не принят

В существующей сессии сайт загрузил 15 Moodle-заданий. Фактический режим:
`chatMode=calendar_advice`, recovery `data-runtime=false`; Calendar сообщает
«Календарь ещё не подключён». На экране плана предлагаются «Планы из чата».
Скриншот: [published-plan-2026-10-22.png](evidence/published-plan-2026-10-22.png).

Это наблюдение одной сессии. Оно не означает, что Google OAuth или отдельная
Calendar-функция сломаны у всех пользователей. Новый consent и реальные записи
не выполнялись. Но обязательный путь Moodle → оценки/окна → recovery proposal →
approval → apply → независимый verify на опубликованной системе не доказан.
Chat Calendar API не заменяет проверку recovery `/api/runs` через Agent Engine.

`setup/PITCH-CLOUD-HANDOFF.md` отсутствует в main и проверенной UI-ветке.
Проверенные ветки не объединены; это соответствует запрету merge, но их проверки
нельзя считать проверками единой опубликованной версии. Хеш полученного браузером
CSS не совпал ни с одной из трёх проверенных версий; это повод запросить точный
serving artifact, а не основание угадывать SHA или объявлять сайт неисправным.
Последний успешный main CI относится только к `4a0858a`:
[GitHub Actions](https://github.com/anuarmaksut711-dotcom/google_hack/actions/runs/39476752791).

**Нужно:** облачный handoff с URL, serving SHA/immutable images, точным Agent
Engine resource и проверенным private `async_query`; реальный полный сценарий,
replay без дублей и проверка двух аккаунтов. Затем повторить UI QA опубликованной
версии, уточнить облачные слайды и записать видео.

### 2. Чистый запуск connected MCP из репозитория/пакета не воспроизводится

`src/campuspulse_recovery/cloud/connected_calendar_mcp.py:27` импортирует
`.live_mcp`, которого нет ни в tracked-исходниках, ни в собранном wheel.
Вызов `create_app()` завершается `ModuleNotFoundError` до чтения конфигурации.
Та же зависимость присутствует в Calendar-ветке.

Deploy-инструкции явно строят overlay поверх уже опубликованных immutable images.
Следовательно, существующий MCP может получать этот модуль из старого образа;
этот аудит **не доказывает его остановку в облаке**. Проблема — невоспроизводимость
чистого запуска и неполная provenance сборки.

**Нужно:** tracked factory/композиция либо точно закреплённый внешний артефакт с
исходниками и smoke test настоящего entry point. Простая сборка wheel это не ловит.

### 3. Стандартный test.lock не обеспечивает collection новой OAuth-проверки

В `c19aee8` файл `tests/lms/test_calendar_oauth_scopes.py:6` напрямую импортирует
`google_auth_oauthlib.flow.Flow`. `requirements/test.lock` и `dev.lock` не содержат
`google-auth-oauthlib`, `requests-oauthlib`, `oauthlib`, хотя pyproject объявляет
их в extras. README и CI устанавливают test.lock и сам пакет с `--no-deps`.
Первый запуск останавливается на collection с `ModuleNotFoundError`.

Для продолжения аудита только в игнорируемую `.venv-pitch` вручную установлены
объявленные версии **1.5.0 / 2.0.0 / 3.3.1**, без изменения lock-файлов.
**Нужно:** владельцу зависимостей пересобрать hash-pinned lock и повторить чистый
CI. Результаты дополненной среды нельзя выдавать за успешную установку по README.

### 4. Calendar-ветка содержит воспроизводимый красный тест

`tests/lms/test_web.py:165`,
`test_dashboard_is_opt_in_and_planning_does_not_use_old_sheet_data` ожидает
«Запись в Google Calendar в этом режиме недоступна». Renderer уже показывает
предложение подтвердить события из чата. Полный и отдельный запуск падают на
одном assert. Сам по себе этот сбой не доказывает поломку Calendar-записи.

**Нужно:** согласовать продуктовый режим, текст и смысл теста, затем повторить
полный прогон. Backend-тест в этой UI-ветке не изменялся.

### 5. Отказ чтения evidence срывает загрузку сохранённого плана

`lms/multiuser.py:168–170` без fallback вызывает `stored_evidence()`;
`cloud/backend.py:145` обращается к worker даже при чтении сохранённой карточки.
В локальном HTTP-воспроизведении: до отказа `/ui/state` = 200; после отказа
evidence = **503**, `storage_outcome_unknown_retry_same_request`; та же сессия
остаётся валидной (`/auth/session` = 200).

**Нужно:** консервативный fallback для недоступности evidence. Сохранённый план
можно показать без verified-успеха; запрещено скрывать AccessDenied, смену сессии
или заменять отсутствие доказательств успешной проверкой. UI уже сохраняет старую
карточку и блокирует действия до успешного reread.

### 6. Контекст и журнал агента неполны

`lms/calendar_projection.py:21–29` передаёт статические «свободные часы неизвестны»,
«запись не подключена» и «оставшееся время неизвестно» независимо от заполненного
planning. UI-ветка убрала misleading Calendar-summary в recovery, но источник
контекста чата требует backend-исправления. В фактическом proposal trace есть
`read_assignments`/`read_calendar`, но нет `solve_repair`. UI не рисует отсутствующий
вызов и не придумывает рассуждения.

**Нужно:** авторизованная сводка planning/Calendar и безопасное фактическое событие
solver в существующем trace, если этот шаг заявляется в демонстрации.
