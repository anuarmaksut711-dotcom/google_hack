# Единый сценарий и импорт пар — проверка 22.10.2026

База этой доработки: `acf869b1eff2e50f2669c3f9f824b7b83cfb534d`, ветка `codex/pitch-ui-demo`.
Работа в отдельном clone `google_hack_pitch_ui`. Пользователь разрешил расширить
исходную UI-зону на серверное распознавание и обязательное исключение сохранённых пар.
Облако, IAM, секреты, зависимости и main не изменялись.

## Результат

Один пользовательский путь: Moodle → пары и время для учёбы → предложенное
расписание → подтверждение версии → Google Calendar → независимая проверка.
Старые пользовательские названия «План изменений»/«Мой план» заменены.
Данные текущих API и runtime-gates сохранены; недоступный исполнитель не выдаёт успех.

PDF/PNG/JPEG до 8 МиБ передаются настроенной мультимодальной модели только по кнопке.
Возвращается черновик до 30 непересекающихся недельных пар. Отсутствующие даты остаются
пустыми. Человек проверяет и исправляет строки, задаёт период и подтверждает проверку
перед сохранением. Ручной ввод работает при отказе распознавания. Файл не хранится
приложением, не включается в историю чата, не получает инструментов выполнения.

Сохранённые пары исключаются из эффективных свободных окон. Границы округляются
консервативно к 15 минутам. Исходные введённые окна и JSON `/api/moodle/planning`
не меняют форму и не затираются вычитанием. Изменение пары, даже одного названия,
входит в версию исходных данных и блокирует старое согласие перед Calendar I/O.
Просроченный/неполный период пар не доказывает свободное время на весь горизонт.
Отсутствующие пары и явно сохранённое пустое расписание различаются.

Optional сохранённые `tool_trace`/`agent_run_id` отображаются под фактическими ответами чата. Без этих полей вызовы не выдумываются; статусы failed/unavailable не становятся успехом. Новый облачный backend пока не объединён, trace UI отдельно проверен на контролируемых сохранённых turns.

Названия заданий в UI берутся из точного сохранённого owner-bound снимка плана.
Идентификаторы остаются в технических подробностях; HTML экранируется.
`applied_unverified` показывается как «Запись пока не подтверждена», без утверждения,
что запись состоялась: существующий backend иногда возвращает этот статус при
безопасном отклонении из-за изменившихся данных, не совершая ни одной записи.

  Итоговые параметры и длительность — в `SCHEDULE-RECEIPT-2026-10-22.json`.
- Recovery offline evaluation: **347 passed**; voice literal-loopback: **53 passed**.
- Сборка wheel/sdist, `pip check`, `deploy/check-recovery-composition.py`: пройдены.
- 81 новая проверка импорта/клиента/пар/композиции/UI. Поведение сначала проверено
  падающими тестами, затем исправлено. Проверены account isolation, CSRF, revoked
  session после await, двойное нажатие, timeout/size/type, нечитаемый ответ модели,
  проверка черновика, даты, потерянный ответ сохранения, stale consent и последний

  были дополнительно установлены после предыдущего аудита. Их ещё нет в test.lock;
  зависимости принадлежат Мерею. Кандидат исправления и запрос — в UI handoff.
  Полный pytest здесь не доказывает чистую установку из неизменённого lock-файла.
- Независимый read-only review: actionable findings не обнаружены.

Полный первый прогон выявил несовместимость аргумента importer с существующим
тестовым legacy-adapter hook. Исправлено сохранением старого вызова installer и
передачей импортёра через trusted account-scoped app.state. Backend-тесты не ослаблялись.
В двух существующих UI-проверках обновлены только строки изменённых подписей.

## Работающий браузер

Штатные производственные auth/session/ADK/MCP/solver/approval/apply/verify с тестовыми
внешними адаптерами. Сервер доступен только на literal loopback; реальные credentials
и внешняя сеть запрещены fixture. Баннер синтетической проверки сохраняется.

Проверено в браузере компьютера:

1. Выбор PDF ничего не отправляет; «Распознать пары» даёт editable draft без дат.
2. Без отметки проверки сохранить импорт нельзя; после проверки сохранение работает.
3. Пары, 90 минут и окно 17.10 22:00–18.10 02:00 восстанавливаются после reload.
4. Пара 22:00–22:20 исключена: первый блок 22:30–23:00, второй 00:00–01:00.
5. Подтверждение и применение — отдельные действия; во время запроса кнопки заблокированы.
6. Независимая проверка дала `verified`; после reload результат восстановился.
7. В журнале видны реальные зарегистрированные `apply_plan` и `verify_plan`/results.
8. Финальные iframe-width 1280 и 390: client/scroll 1260/1260 и 370/370 соответственно
   (20px занимают scrollbars). Горизонтального переполнения документа нет;
   таблица имеет собственную горизонтальную прокрутку. Консоль нового узкого tab: без warning/error.

HTTP acceptance независимо прошёл импорт → save → proposal → approval → apply → verify.
Повтор того же apply-запроса не меняет counters: 2 тестовые Calendar mutations,
1 apply_plan, 1 verify_plan, 8 Calendar reads. Это один HTTP-run; браузерные запуски
в отдельных временных процессах не объединяются с ним в один continuous run.

Доказательства: `evidence/schedule/`, `SCHEDULE-RECEIPT-2026-10-22.json`.
Презентация: 7 редактируемых слайдов PPTX, 7 страниц PDF. Все PDF-страницы просмотрены;
исправлен перенос слова на слайде 3. Package/layout/font/import validators: 0 findings.
Реальный PowerPoint-render не запускался.

## Границы и оставшаяся приёмка

Реальный Gemini OCR не вызывался: synthetic model response не измеряет точность
распознавания. Нужны smoke-проверки реального PDF и снимка одной группы с настроенной
моделью, квотой и privacy-настройками провайдера.

Он описывает read-only study-agent, оставляет live acceptance pending и не включает
Calendar writes/recovery. Подробности объединения — `CLOUD-FACTS-2026-10-22.md` и UI handoff.
Реальное облачное видео не записано по этой причине; `VIDEO-STATUS.md` содержит условия.

разрешённые тестовые Calendars, отсутствие пересечений/дублей, отзыв/смена сессии,
перечитывание результата и запись видео фактически пройденного сценария.
