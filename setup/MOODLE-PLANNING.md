# Серверное планирование заданий Moodle

Режим `cloud` с настроенным `moodle` использует сохранённый REST-снимок LMS,
введённые студентом оценки времени и доступные окна. Импорт Moodle, OAuth,
Google-клиенты и фронтенд этим изменением не заменяются. Режимы календарного
экспорта ICS и локального multiuser-чата сохраняют своё прежнее поведение.

## Поток данных

1. Существующий sync worker сохраняет задания Moodle.
2. Авторизованный студент сохраняет оставшееся время и свободные окна через API ниже.
3. `POST /api/runs` запускает существующий recovery-агент. Его `read_assignments`
   читает Moodle-кэш, а `read_calendar` — прежний календарный адаптер.
4. Solver строит план в пределах существующего горизонта 72 часов. Backend
   независимо проверяет и сохраняет предложение.
5. Существующие `/api/approval` и `/api/runs/continue` сохраняют подтверждение
   точной версии и запускают прежний процесс применения и проверки календаря.

Снимки заданий имеют отдельный идентификатор источника `moodle:<hash>`.
Они не выдаются за данные Google Sheets. Привязку источника выбирает доверенный
серверный запуск для backend, agent и MCP; браузер не передаёт эту привязку.

## Получение настроек

`GET /api/moodle/planning` требует существующую сессию входа. Параметры query запрещены.
Для нового пользователя возвращается:

```json
{
  "schema_version": "1.0",
  "working_windows": null,
  "estimates": [],
  "revision": 0,
  "updated_at": null
}
```

Идентификаторы заданий для редактирования берутся из существующего `GET /api/moodle`.
Статусы, оценки и дедлайны по-прежнему принадлежат Moodle; этот API их не изменяет.

## Сохранение входных данных

`POST /api/moodle/planning` требует JSON, сессионные cookies, существующие заголовки
`Origin` и `X-CSRF-Token`. Пример тела; даты и task ID нужно заменить актуальными:

```json
{
  "expected_revision": 0,
  "working_windows": [
    {"start": "2026-10-20T10:00:00+05:00", "end": "2026-10-20T12:00:00+05:00"},
    {"start": "2026-10-21T14:00:00+05:00", "end": "2026-10-21T16:00:00+05:00"}
  ],
  "estimates": [
    {"task_id": "assign:9", "remaining_minutes": 90},
    {"task_id": "quiz:12", "remaining_minutes": 30}
  ]
}
```

Ответ — полное сохранённое состояние, как в GET, с увеличенным `revision`
и серверным `updated_at`. Следующий POST передаёт полученную версию как
`expected_revision`. Одновременное редактирование устаревшей версии возвращает
409: перечитайте GET и согласуйте изменения перед повторным сохранением.
После неопределённого сетевого исхода сначала перечитайте GET.

Обновления частичные. Оценки для остальных заданий сохраняются:

```json
{
  "expected_revision": 1,
  "estimates": [{"task_id": "assign:9", "remaining_minutes": 45}]
}
```

- Пропущенный `working_windows` сохраняет предыдущие окна.
- `working_windows: null` означает, что доступное время неизвестно.
- `working_windows: []` означает, что свободных окон нет.
- Окна — конкретные интервалы с часовым смещением, а не еженедельное расписание.
  Границы должны попадать на четверть часа; пересечения запрещены. При расчёте
  окна обрезаются текущим горизонтом 72 часов. Истёкшие окна не переносятся автоматически.
- `remaining_minutes: null` возвращает оценку в неизвестное состояние.
- `remaining_minutes: 0` явно исключает работу из нового планирования; запись
  в Moodle не выполняется. Допустимы целые значения от 0 до 100000.
- Положительная оценка оставшегося времени учитывается даже для `submitted`/`graded`,
  например для повторной попытки. Без пользовательской оценки `submitted` исключается.
  `graded` и нулевая оценка сами по себе не доказывают завершение: без оценки времени
  такая работа требует уточнения. Явный `null` также остаётся неизвестным объёмом работы.
- Отсутствующий дедлайн или оценка времени не заменяются предположениями.
- Один POST принимает до 100 оценок и до 32 окон; действует общий лимит тела 16 KiB.
  Сохранённое состояние поддерживает до 500 оценок. Несуществующие task ID отклоняются.
- `revision`, `updated_at`, owner, URL, аккаунт и идентификаторы внешних ресурсов
  нельзя подставить в запрос сохранения.

## Результаты и ошибки

Неполные входные данные дают `needs_input`, нехватка времени — `infeasible`.
В этих случаях исполняемое предложение и согласование не создаются.
Устаревший, отключённый или ошибочный Moodle-кэш не подменяется пустым списком заданий.

Изменение доступных окон проверяется перед принятием кандидата и перед применением
плана. Ревизия пользовательского ввода и текущее состояние заданий проверяются также
в транзакции выдачи разрешения на каждую запись и последней проверке перед Calendar I/O.
Изменения требуют нового предложения и нового подтверждения. Даже сохранение тех же
значений с новой ревизией консервативно требует нового плана. Обычное обновление
Moodle-снимка без изменения объёма работы/дедлайнов план не отменяет.
Результат неизвестной записи в Calendar по-прежнему не разрешает слепое повторение.

Для API настроек используются существующие коды backend:

| HTTP | Значение |
|---|---|
| 200 | Состояние прочитано или сохранено |
| 400 | Некорректные поля, типы, окна, query или тело запроса |
| 403 | Нет действующей сессии, неверный Origin/CSRF или запрещённая привязка |
| 409 | Конфликт версии, нет Moodle-снимка или task ID отсутствует в нём |
| 503 | Исход операции хранилища не подтверждён |

## Проверка

```sh
python -m pytest tests/lms/test_planning.py tests/lms/test_planning_backend.py tests/lms/test_planning_composition.py -q
```

Сквозные тесты используют настоящие ADK, локальный MCP transport, solver,
проверку предложения, серверные grants и репозитории. Модель, вход в аккаунт,
Calendar и документы синтетические; внешняя сеть и настоящие credentials запрещены.
Эти проверки не подтверждают работу реальных Google/Moodle аккаунтов или облачный deployment.
