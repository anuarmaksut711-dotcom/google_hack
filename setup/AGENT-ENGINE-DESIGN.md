# Серверный runtime для Agent Engine

Цель: подготовить существующий recovery worker к запуску как custom Python agent
в Vertex AI Agent Engine. Это серверная часть второго deliverable кейса GDG.
Фронтенд, клиенты Moodle/Calendar/Gemini, IAM и действующий Cloud Run transport
в эту задачу не входят. Фактическое облачное развёртывание выполняет команда подключений.

## Выбранный подход

Отдельный `AgentEngineRuntime` предоставляет только `async_query(invocation,
service_token)`. Внутри процесса он вызывает существующий приватный ASGI worker
через локальный ASGI transport. Это сохраняет настоящую проверку подписи/аудитории
сервисного ID-токена, чтение живой сессии, одноразовый grant и все проверки apply.
Токен адресован существующему `agent_origin`; это логическая аудитория проверяющего
worker, HTTP-запрос на этот адрес оболочка не отправляет. Платформенный OAuth для
самого Agent Engine остаётся отдельной обязанностью вызывающего backend.

JSON не может задавать owner, session, run, tool, plan или внешние ресурсы: они
разрешаются по серверному grant. Модель не получает ни grant, ни сервисный токен.
Оболочка не принимает текст пользовательского запроса и не трактует ответ модели
как доказательство применения. Используется существующий ADK recovery loop.

Конструктор хранит только проверенную конфигурацию и не создаёт Google-клиентов.
Для этого runtime требуется явный Vertex provider. Клиенты и ASGI app создаются
на один вызов и закрываются через lifespan даже при ошибке или отмене. Сериализация
восстанавливает объект из конфигурации, без клиентов, сессий или токенов вызовов.
У вызова есть ограничения размера и времени; автоматических повторов записи нет.

## Подготовка пакета

Отдельный offline CLI проверяет готовый wheel, закреплённый cloud lock и настройки,
затем создаёт новый приватный каталог с копиями артефактов и manifest SHA-256.
В manifest явно указан статус `prepared_not_deployed`. Подготовка не делает ADC,
сетевых запросов, upload, IAM или `agent_engines.create`. Существующие локальные
блокировки в старых deploy/query скриптах сохраняются.

## Критерии проверки

- SDK 1.165.1 распознаёт ровно одну async operation и её два параметра.
- Конструктор, pickle roundtrip и offline CLI работают без credentials/сети.
- Неверный токен, grant, повторное использование и отозванная сессия не дают dispatch.
- Настоящие ADK, MCP, solver и approval проходят локальный Moodle propose/apply/verify.
- Ошибки, отмена и превышение лимитов закрывают ресурсы и не повторяют работу.
- Повреждённые/неподходящие артефакты не создают готовый пакет.
- Полный pytest, Firestore Emulator, offline evaluations и сборка проходят.

Этот результат не является доказательством облачного deployment: для закрытия
критерия кейса нужны настоящий `reasoningEngines/...`, доступный endpoint и живое
демо через него. Переход backend на SDK transport остаётся за командой подключений.
