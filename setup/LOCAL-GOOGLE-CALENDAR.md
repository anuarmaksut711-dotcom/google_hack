# Локальное подключение Google Calendar

Этот режим запускает существующее Python-приложение с отдельным подключением
основного календаря пользователя. Он читает события на следующие 72 часа,
показывает ссылки на события и журнал `read_calendar`. Доступ только для чтения;
создание и перенос учебных блоков остаются в существующем recovery-процессе
с сохранённым планом, подтверждением и проверкой результата.

## Запуск

Python 3.12, Windows PowerShell:

```powershell
py -3.12 -m venv .venv-calendar
.\.venv-calendar\Scripts\python.exe -m pip install -e '.[local-calendar]'
.\run-google-calendar.ps1
```

В текущем рабочем окружении launcher также находит уже установленный Python
из `campuspulse/recovery_app/.venv-release-test`. Три дополнительные OAuth-пакета
установлены отдельно в игнорируемую `.validation/calendar-deps`, без изменения
общего окружения. Для обычной установки используйте extra выше.

Страница: <https://127.0.0.1:8981/google-calendar>. Сервер слушает только loopback.
Локальный HTTPS использует самоподписанный сертификат; переход через
предупреждение браузера выполняет пользователь. `-Background` запускает сервер
без отдельного окна. Процесс и журналы находятся в каталоге состояния ниже.

## Первое подключение

Проект по умолчанию: `project-e25873c6-e889-40bb-86d`, из актуальной записи
`setup/CHAT-PAGES-DEPLOYMENT.md`. Другой проект задаётся явно параметром `-Project`.
Никаких команд развёртывания, изменения IAM или включения API launcher не выполняет.

1. В Google Cloud нужного проекта включите Google Calendar API.
2. В Google Auth Platform настройте аудиторию; для режима Testing добавьте свой
   аккаунт в тестовые пользователи. Для доступа используется scope
   `https://www.googleapis.com/auth/calendar.readonly` и `openid` для проверки
   аккаунта. Вход через Google сам по себе не выдаёт Calendar-разрешение.
3. В OAuth-клиенте типа Web application добавьте JavaScript origin
   `https://127.0.0.1:8981` и redirect URI
   `https://127.0.0.1:8981/auth/google-calendar/callback`.
4. Скачайте JSON обновлённого OAuth-клиента. Выберите его на локальной странице.
   Приложение проверит проект, Google endpoints и точный redirect URI.
   Можно импортировать файл и через `-ClientFile 'C:\path\client.json'`.
5. Откройте `/google-calendar`. При первом входе кнопка «Войти через Google и
   подключить календарь» откроет обычную страницу Google без всплывающего окна.
   Предоставьте доступ для чтения. Подписанный Google ID token проходит существующую
   проверку nonce, аудитории и одноразового входа; затем создаётся обычная сессия
   приложения и сохраняется подключение календаря.
6. Если вы уже вошли в приложение через Google либо почту, используйте страницу
   `/google-calendar` или ссылку в `/settings`. Локальные аккаунты и подключения
   отделены от облачного сайта.

Если вход в приложение выполнен через Google, подключаемый Google subject
должен совпасть с аккаунтом входа. При входе по почте отдельное согласие Google
привязывает доказанный Google-аккаунт к текущему локальному аккаунту.
`primary` разрешается через OAuth самого пользователя в точный Calendar ID;
service account для выбора основного календаря не используется.

Пока нет JSON и успешного Google OAuth, подключение не завершено и реальные
события не прочитаны. Экран настройки и автоматические тесты не доказывают
доступность реального Calendar.

## Хранение и границы

Состояние: `%LOCALAPPDATA%\CampusPulse\google-calendar\<project>`.
Используется существующий зашифрованный `SqliteDocuments`; клиентский секрет,
refresh token, PKCE verifier и nonce не попадают в репозиторий. Ключ шифрования
также хранится в локальном профиле Windows, поэтому этот каталог предназначен
для текущего доверенного пользователя компьютера. В этом режиме Firestore и
Secret Manager не используются; облачный recovery сохраняет свои зависимости.

Одноразовый OAuth state имеет срок пять минут и привязан к серверной сессии.
Проверяются PKCE S256, nonce, подписанный ID token, аудитория и Google subject.
Callback выполняет отдельный same-origin POST с CSRF-проверкой; внешний GET
не предоставляет доступ. Обмен токена и чтение Google происходят вне транзакций.
Выход во время обмена блокирует сохранение результата.

Calendar-запросы проходят через локальный инструмент официального Python MCP
SDK (`FastMCP.call_tool`, диспетчер в том же процессе). Это локальная композиция
без второго HTTP-сервиса и без удалённого MCP transport. Облачный MCP и Agent
Engine не изменяются; локальное подключение не является новым облачным deploy.

Временные метки имеют timezone, интервалы полуоткрытые. Дата окончания all-day
события исключается. `singleEvents=true` разворачивает повторяющиеся события;
страницы читаются до конца, максимум 2500 событий. Неполные или некорректные
данные дают ошибку вместо сообщения об успешном чтении. Содержимое событий
выводится как текст и не передаётся в чат этим подключением. Наличие события
в прошлом не считается выполненной работой.

«Отключить локально» убирает активный сохранённый токен из приложения. Это не
отзывает разрешение на стороне Google; отзыв выполняется пользователем в
настройках Google-аккаунта. Запоздалое чтение не восстанавливает отключённый токен.

Официальные руководства: [Google OAuth для web-приложений](https://developers.google.com/identity/protocols/oauth2/web-server),
[Calendar scopes](https://developers.google.com/workspace/calendar/api/auth).

## Фактическая локальная проверка — 20 октября 2026

В проекте `project-e25873c6-e889-40bb-86d` подтверждено включение Calendar API.
Создан отдельный Web OAuth-клиент `CampusPulse Local Calendar`; текущий клиент
опубликованного сайта сохранён. Настроены локальный origin и callback выше,
тестовая аудитория и scope Calendar только для чтения. Пользователь отдельно
подтвердил создание клиента и доступ к календарю.

Реальный Google OAuth завершён через обычную страницу, подписанный ID token
проверен сервером. Основной Calendar ID получен от Google через пользовательский
OAuth. В 23:09 по Asia/Qyzylorda интерфейс выполнил реальный `read_calendar`:
успех, **0 событий в следующих 72 часах**. Журнал в UI содержит run/call ID,
длительность и фактический результат. Проверены кнопка обновления, восстановление
страницы и подключение после перезапуска сервера; консоль без ошибок.

Регрессия: 588 тестов прошли, один тест требует отдельного Firestore emulator
и пропущен. После последнего изменения CSP повторно прошли 34 связанные
проверки и выполнено реальное чтение через страницу.

Эта проверка подтверждает локальное чтение. Calendar не изменялся; cloud OAuth
и перенос подключения в Firestore/Secret Manager ещё не выполнялись. Облачный
сайт не развёртывался: решение о деплое остаётся за пользователем после просмотра.
